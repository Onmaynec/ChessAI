# Chess AI 0.3 — методика Self-Play / PPO

## Реальное состояние проекта

`neural.selfplay` является самостоятельным RL-тренером, который использует **ту же** `ChessNet`, что и v0.2, но больше не пытается предсказывать только ходы слабого baseline. Стартует с включённого supervised-чекпойнта `models/neural_best.pt` (не с нуля по умолчанию), затем обновляет модель по результатам её собственных партий. В тренировке нет Stockfish, внешних LLM/AI API или GUI шахматного приложения.

## Состояния, политика, награда

- Состояние `s`: `19×8×8` encoded FEN, включая чей ход, рокировки и поле взятия на проходе.
- Действия: 4672 логитов, распределение нормировано **только по легальным UCI-ходам** C++-движка.
- Выбор: `Categorical(softmax(logits_legal / temperature))`; сохранение выбранного `a` и его `old_logp`.
- Value: `v(s)` — прогноз результата **с точки зрения стороны, которой ходить**, в `[-1, 1]`.
- Reward: `z(s) = +1` для победившей стороны; `−1` для проигравшей; `0` для завершённой ничьей.
- Termination: C++ `outcome()` (мат, пат, недостаточно материала, пяти-/трёхкратное повторение, правила 75/50 ходов), иначе `max_plies_unfinished` без reward.

## Алгоритм

Для каждой свежей итерации:

1. Создаём `games_per_iteration` независимых досок; одновременно обрабатываем `parallel` позиций одной батчевой моделью. Один постоянный C++-процесс с командами `new ID`, `step ID UCI`, `drop ID` экономит накладные расходы.
2. Собираем состояния, legal moves, выбранные действия, old log-probabilities, predicted Value, а после окончания партии — целевые returns `z`.
3. Фильтруем **только завершённые партии**. Для каждого шага `A = z - v_old`, масштабирование по std (без вычитания среднего, чтобы не смещать знак).
4. На `ppo_epochs` проходов и minibatches вычисляем `r = exp(log π_new(a|s) - log π_old(a|s))` и

   `loss_policy = -mean(min(r*A, clip(r, 1-ε, 1+ε)*A))`.

5. `loss_value = MSE(v_new, z)`; `loss = loss_policy + value_weight*loss_value - entropy_weight*entropy`.
6. Градиенты ограничиваются по норме 1.0; оптимизатор AdamW обновляет все веса модели.
7. Сохраняем checkpoints, `metrics.jsonl`, `games.jsonl`, `experience.jsonl` и статус.
8. Если включены arena games, играем сбалансированную по цветам серию **против фиксированной модели**, сохраняем score по завершённым играм.

Это ранний on-policy actor-critic/PPO, а не полная AlphaZero: пока нет MCTS и улучшенной search-policy. Поскольку партия может закончиться ничьей, reward 0 — настоящий, но слабый сигнал. На одной RTX 3050 невозможно гарантировать уровень Stockfish или сверхчеловеческую силу: необходимы более сильный поиск, гораздо больше обучающего опыта и проверочные турниры.

## Повторения, ничьи, незавершённые партии

Внутреннее правило автоматической заявки на ничью при трёхкратном повторении или 50 ходах задано явно в `src/chess.cpp`. Оно отражает обучающую политику агента, а не автоматическое завершение всех человеческих шахматных матчей. Состояние с `result='*'` не получает награду и не создаёт policy samples. Это принципиально: выдавать незавершённый матч за ничью было бы ложной разметкой и могло ухудшить обучение.

## Достоверность измерений

- Наблюдаемые скорости `games/s` и `plies/s` считаются на итерации и включают время self-play, оптимизации и arena (если включена).
- Значения loss относятся к текущему on-policy батчу. Монотонного уменьшения не требуется, взаимное сравнение лоссов при разных настройках наград/температуры некорректно.
- Проверочная метрика Arena score отделена от обычной самоигры. При малой выборке не доказывает рост силы.
- `experience.jsonl` — аналитический архив всех завершённых траекторий; он **не используется для off-policy policy gradient** последующих итераций.
- Resume восстанавливает веса и оптимизатор, но **не точный RNG state**. Идентичность результатов при повторе не гарантируется.
- Даже если обучение идёт очень быстро, виртуальные шахматные часы не являются единицей скорости; измеряйте реально обработанные партии и позиции.

## Рекомендуемый практический путь

1. Прогнать короткий профиль 2×2 партии, проверить UI и наличие файла weights.
2. Прогнать 10–30 итераций с `max_plies` 240–320, увеличить количество законченных партий.
3. Включить `arena_games>=4`, накопить достаточно завершённых проверочных матчей.
4. Анализировать не только loss, но и долю завершённых партий, распределение причин ничьих, состязания с постоянным оппонентом, качество игры на разных начальных позициях.
5. Лишь после этого добавлять MCTS/batched search и более эффективные data pipelines.
